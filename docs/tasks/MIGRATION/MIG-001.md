# MIG-001 — Migration toolkit skeleton

**Status:** done
**Spec:** `docs/specs/13_MIGRATION.md`
**Code:** `migration/`

## Goal

A repeatable Odoo → Tryton migration pipeline that can be rehearsed today,
before the Tryton modules exist, and that refuses to produce a silent wrong
answer.

## Delivered

* `extract → stage → map → build → load → reconcile`, each stage writing an artifact.
* Read-only SQL extraction into a JSONL snapshot; 13 datasets; `probe` detects the Odoo version and adapts the queries.
* PostgreSQL `stg` schema — one generic landing table plus a typed view per dataset, generated from the dataset catalogue.
* Reviewable CSV mapping tables with an approval workflow; accounting mappings require a named reviewer.
* Pure-function transforms for opening balances, open AR, open AP and approved open POs.
* Idempotent loads keyed by `migration_ref`; a rerun reports `unchanged`, never duplicates.
* Nine reconciliation checks, a markdown report with a sign-off block, and exit codes that gate cutover.
* 126 tests, no database required.

## Decisions made here

1. **The extracted JSONL is the snapshot.** Everything downstream reads it, never the source, so rehearsals are repeatable and diffable.
2. **The opening entry excludes the AR and AP control accounts.** Those balances come from open items, invoice by invoice; `trial_balance` proves the halves add back to the source GL.
3. **Inventory never passes on Odoo data.** `inventory_value` stays `SKIPPED` until an approved physical count is loaded.
4. **Unimplemented paths raise.** The `tryton` target and the `odoo_rpc` / `csv` sources are declared stubs with implementation contracts in their docstrings — not half-working code.
5. **No fallbacks in mapping.** An unmapped or unapproved value stops the load rather than defaulting to the source value.
