# CAPITAL NUTRITION ERP — CORE SCREEN SPECIFICATIONS

Companion to `11_UI_UX.md` and `11_UI_UX_STANDARDS.md`. This document specifies
the screens named in `11_UI_UX.md` §Core screens. Every rule in
`11_UI_UX_STANDARDS.md` applies to every screen here and is not repeated.

**Reading this document.** Column lists are the *default visible* set. Columns
marked `(opt)` ship as `optional="1"`, hidden by default. The column budget is
nine (Standards §4.1); the `expand` column is marked `(exp)`.

**Dependency note.** Field names are not given, because the data model is not
settled — `01_ARCHITECTURE.md` and the domain specifications for Products,
Inventory, Customers and Sales do not yet exist. This document specifies *what
information appears where and why*. Binding it to concrete Tryton fields is the
first step of each implementation task, and any place where the required
information does not exist in the model is a finding to raise, not a field to
invent.

---

## 1. Dashboard

`11_UI_UX.md` is explicit: **operational exceptions and high-value metrics
rather than decorative charts.**

### 1.1 Design intent

The Dashboard answers one question: *what needs a human today?* Every element
is a count of things that are stuck, late, or wrong, and every count is
clickable through to the filtered list that produced it.

A number on this screen that a user cannot act on does not belong on this
screen.

### 1.2 Content

**Exceptions block** — each row is a count, a label, and a drill-through. A
count of zero renders muted; a non-zero count renders `warning`, or `danger`
where noted.

| Exception | Visual | Drills to |
|---|---|---|
| Integration messages failed | `danger` | Integration → Failures |
| Integration dead letters | `danger` | Integration → Dead Letters |
| Receipts with discrepancies | `danger` | Purchasing → Receipts, discrepancy filter |
| Vendor bills failing three-way match | `danger` | Purchasing → Discrepancies |
| Sales orders on hold | `warning` | Sales → Orders, on-hold filter |
| Sales orders unshipped past promised date | `warning` | Sales → Orders, late filter |
| Purchase orders overdue from vendor | `warning` | Purchasing → Orders, overdue filter |
| Customer invoices overdue | `warning` | Accounting → Customer Invoices, overdue filter |
| Vendor bills due this week | `warning` | Accounting → Vendor Bills, due filter |
| Items below minimum | `warning` | Inventory → Reorder |
| Unreconciled bank items | `warning` | Accounting → Reconciliation |
| Open period past close date | `warning` | Accounting → Period Status |

**Metrics block** — a small number of figures that give the day its shape.
Values only, no charts: orders to ship today, orders shipped today, receipts
expected today, AR total outstanding, AP total outstanding, current period
status.

### 1.3 Rules

- **No charts in the first release.** If a chart is later shown to answer a
  question a number cannot, it goes through Standards §17.
- Every count drills through to a real filtered list, and the list it opens
  must produce exactly that count. A drill-through whose row count differs from
  the tile is a defect.
- Nothing on the Dashboard is editable.
- The Dashboard loads within two seconds. Counts that cannot be produced
  quickly are dropped, not made slow (Standards §11).

### 1.4 Open question

**OPEN — implementation mechanism.** Tryton's native board view may or may not
support this layout acceptably. Three candidate approaches: a board view of
narrow tree views; a dedicated dashboard model with computed count fields; a
list of exception records generated by a scheduled task. This must be decided
by ADR before **UI-010**, and the decision governs how much the Dashboard can
later grow.

### 1.5 Acceptance

A user opening the ERP in the morning can tell within ten seconds whether
anything is wrong, and reach the first thing needing attention in one click.

## 2. Sales

### 2.1 Order list

**Default filter:** not cancelled, not fully invoiced-and-shipped.
**Default sort:** order date ascending (work list).
**Named filters:** *To Confirm*, *To Ship*, *Late*, *On Hold*, *To Invoice*,
*All*.

| # | Column | Notes |
|---|---|---|
| 1 | Order Number | fixed width |
| 2 | Order Date | fixed width |
| 3 | Customer | `(exp)` |
| 4 | Customer Reference | their PO number — what they quote on the phone |
| 5 | Promised Date | drives the *Late* filter |
| 6 | Fulfillment | see §2.2 |
| 7 | Payment | see §2.2 |
| 8 | Total | `sum="1"` |
| 9 | State | last, always |

`(opt)`: warehouse, salesperson, shipping method, channel/source (web vs
manual — matters once Magento is live), currency, created by.

**Row visual:** `danger` if on hold or past promised date and unshipped;
`warning` if partially shipped or partially paid; `success` if shipped complete
and paid; `muted` if cancelled.

### 2.2 Fulfillment and payment state

`11_UI_UX.md` names these as first-class. They are shown as their own columns
because the order's own state does not answer them: an order can be Confirmed
and be any combination of unshipped/part-shipped/shipped and
unpaid/part-paid/paid.

- **Fulfillment:** None / Partial / Complete / Back-ordered
- **Payment:** Unpaid / Partial / Paid / Overpaid

Both are words, not icons, and both use the same vocabulary everywhere they
appear (Standards §1, §12.3).

### 2.3 Order detail

**Header:** order number, state, customer, order date, customer reference,
promised date.

**Action row:** primary is the next happy-path step for the current state —
Confirm (draft), Ship (confirmed), Invoice (shipped). Secondary: Hold, Release,
Duplicate. Right-side: Cancel.

**Notebook:**

1. **Lines** — editable-bottom. Columns: item, description, quantity, unit,
   available at time of entry, unit price, discount `(opt)`, tax `(opt)`, line
   total. **Available** is shown at line entry because promising stock that is
   not there is the most expensive error a salesperson makes, and it must be
   the availability figure defined in Standards §1.3, not on-hand.
2. **Related** — shipments, invoices, payments. Read-only, drill-through.
3. **Other Info** — warehouse, shipping method, terms, salesperson, addresses.
4. **Notes** — free text and attachments.

**Totals block** (outside the notebook): untaxed, tax, total, amount paid,
balance due.

**Relates:** customer history, customer aging, shipments, invoices, GL move
where posted.

### 2.4 Customer history

Reached by relate from an order or from the customer record — not a menu item.

Shows, for one customer: orders, invoices, payments, aging summary, and the
items they buy with last price and last order date. The last of these is what a
salesperson actually wants on a call, and it is the reason this screen exists
rather than three separate relates.

**Default sort:** most recent first (reference list).

### 2.5 Acceptance

A salesperson can, on a phone call: find the customer's last order, see what
they bought and at what price, see whether they owe money, create a new order,
and know at line entry whether the stock is available to promise — without
leaving the screen they started on.

## 3. Purchasing

Driven by `06_PURCHASING.md`. That specification's acceptance list is the
functional test; this section is how it is presented.

### 3.1 PO list

**Default filter:** not cancelled, not fully received-and-billed.
**Default sort:** expected date ascending.
**Named filters:** *To Send*, *Awaiting Receipt*, *Partially Received*,
*Awaiting Bill*, *Discrepancies*, *All*.

| # | Column | Notes |
|---|---|---|
| 1 | PO Number | |
| 2 | Order Date | |
| 3 | Vendor | `(exp)` |
| 4 | Expected Date | vendor lead time drives this |
| 5 | Receipt | None / Partial / Complete / Over |
| 6 | Billing | None / Partial / Complete |
| 7 | Match | OK / Discrepancy / Not Applicable |
| 8 | Total | `sum="1"` |
| 9 | State | |

`(opt)`: warehouse, buyer, vendor reference, currency, created by.

**Row visual:** `danger` on match discrepancy or over-receipt; `warning` when
partially received or past expected date; `success` when received and billed
and matched; `muted` when cancelled.

### 3.2 PO detail

**Header:** PO number, state, vendor, order date, expected date, vendor
reference.

**Action row:** primary by state — Confirm, Send to Vendor, Receive, Create
Vendor Bill. Secondary: Duplicate. Right: Cancel.

**Notebook:**

1. **Lines** — editable-bottom. Columns: item, vendor SKU, description,
   quantity ordered, unit, case pack, quantity received, quantity billed, unit
   price, price break applied, line total.

   Two of these columns exist specifically because `06_PURCHASING.md` requires
   them and getting them wrong is expensive:

   - **Case Pack** is visible at line entry, not buried. Ordering a
     non-multiple of case pack is a warning (Standards §9.2), not silently
     accepted and not hard-blocked — vendors do occasionally break case.
   - **Price Break Applied** shows *which* break the system selected. A buyer
     must be able to see that the system picked the right one without opening
     the vendor price list. `06_PURCHASING.md` acceptance step 3 is not
     satisfiable if this is invisible.

2. **Receipts** — the receipts against this PO, with received quantities.
3. **Bills** — the vendor bills against this PO, with match status.
4. **Other Info** — warehouse, terms, buyer, addresses, lead time.
5. **Notes**

**Totals:** untaxed, tax, total, amount received (valued), amount billed.

### 3.3 Receiving

**Default filter:** pending and in progress.
**Default sort:** expected date ascending.
**Named filters:** *Expected Today*, *Overdue*, *In Progress*, *With
Discrepancy*, *All*.

**Receipt detail — lines:** item, vendor SKU, quantity expected, quantity
received, unit, lot, expiry `(opt)`, location, discrepancy.

Receiving rules:

- **Quantity received defaults to quantity expected.** The common case is
  receiving what was ordered; making the receiver retype it invites
  transcription errors and wastes the most repeated interaction in the
  warehouse.
- **Lot capture is required where the item is lot-tracked**, enforced at
  receipt, not later. A nutrition business cannot retrofit lot data.
- **Over-receipt is a warning that states the variance** in both quantity and
  percentage, then permits it if confirmed. `06_PURCHASING.md` requires
  over-receipt handling, and blocking it outright means the warehouse invents a
  workaround.
- Receiving is fully keyboardable (Standards §15).

### 3.4 Discrepancies

A dedicated screen, because `06_PURCHASING.md` acceptance step 7 makes
resolving discrepancies an explicit user task and it must not be scattered
across three other screens.

One row per discrepancy. Columns: type (quantity / price / tax / missing
document), PO number, vendor `(exp)`, item, expected, actual, variance,
variance %, value impact, age in days, state.

**Default sort:** value impact descending. The largest money problem is at the
top — this is the one list in the ERP not sorted by date, deliberately.

**Actions:** Accept Variance, Request Credit, Adjust Bill, Escalate — each
recording who resolved it and how (Standards §14).

### 3.5 Vendor history

Reached by relate. Per vendor: purchase orders, receipts, bills, payments,
aging, on-time delivery record, and the vendor's item list with SKU, current
price, breaks, case pack and lead time.

### 3.6 Acceptance

The nine numbered steps of `06_PURCHASING.md` acceptance are each completable
without navigating to a menu mid-task, and step 3 — confirming the correct
price break was selected — is visible on the order line itself.

## 4. Inventory

### 4.1 Stock lookup

The most-used screen in the warehouse. It answers "do we have it, where, and
how much can I promise" in one place.

**Search-first.** Opens with the search focused rather than listing everything;
listing all stock is never what the user wants.

Columns: item code, description `(exp)`, warehouse, location, on hand,
reserved, available, unit, lot `(opt)`, expiry `(opt)`.

The three quantity columns are always all three, always labelled per Standards
§1.3, each with `help`. This is the screen that rule exists for.

`sum="1"` on all three quantity columns.

### 4.2 Warehouse / location view

Hierarchical tree of warehouses and locations with roll-up quantities, so a
user can expand from warehouse to location without a filter.

`tree_state` is used so the expansion the user works with persists.

### 4.3 Lot information

Per lot: item, lot number, quantity on hand by location, expiry date, receipt
date, source receipt and vendor, and every movement of that lot.

**Traceability is the point.** From a lot, a user must reach every customer
shipment that included it, and from a shipment, every lot that went into it.
For a nutrition business this is a recall requirement, not a convenience, and
it is the acceptance test for this screen.

**Row visual:** `danger` when expired, `warning` when within the expiry warning
window.

**OPEN — expiry warning window.** Not defined anywhere in the specifications.
Needs a business decision before **UI-024**.

### 4.4 Movement history

Every stock move: date, item `(exp)`, from location, to location, quantity,
unit, lot `(opt)`, source document, state.

**Default filter:** last 90 days.
**Default sort:** date descending (reference list).

Every row drills through to its source document. A move whose source cannot be
reached is an integrity problem worth surfacing, not hiding.

### 4.5 Availability

Forward-looking, per item: on hand, reserved, available, expected in (with
dates, from confirmed POs), committed out (with dates, from confirmed sales
orders), and projected available by date.

This is what makes the reorder mechanism in `06_PURCHASING.md` reviewable by a
human before an order is placed — that specification is explicit that orders
are not placed automatically without an approved workflow, which means a person
must be able to see and trust these numbers.

### 4.6 Acceptance

A warehouse user can determine what is available to promise, where it is, and
which lot to pick, in one screen. A recall can be traced from lot to every
affected customer shipment.

## 5. Accounting

Driven by `03_ACCOUNTING.md`. Its acceptance criteria — trial balance, P&L,
balance sheet, AR, AP and inventory accounting all tying — are the functional
test. This section makes them reviewable.

### 5.1 Customer invoices

**Default filter:** unpaid or partially paid.
**Default sort:** due date ascending.
**Named filters:** *Draft*, *To Post*, *Unpaid*, *Overdue*, *Paid*, *All*.

Columns: invoice number, invoice date, customer `(exp)`, due date, total
`sum="1"`, paid `sum="1"`, balance `sum="1"`, state.
`(opt)`: source order, terms, currency, period, posted by.

**Row visual:** `danger` overdue; `warning` due within seven days; `success`
paid; `muted` cancelled.

### 5.2 Vendor bills

Same shape, vendor side, plus a **Match** column (OK / Discrepancy) carrying
the three-way match result from `06_PURCHASING.md`, and a filter for
*Discrepancies*.

### 5.3 Payments

Columns: payment number, date, party `(exp)`, direction (Received / Paid),
method, amount `sum="1"`, allocated `sum="1"`, unallocated `sum="1"`, state.

Unallocated payments are surfaced as their own named filter and as a Dashboard
exception candidate. Money received and not applied is a reconciliation problem
that compounds quietly.

### 5.4 Reconciliation

Two panes: unreconciled statement items on one side, unreconciled ledger
entries on the other, with suggested matches highlighted and a running
difference that must reach zero.

The difference is visible at all times. Confirmation is required to commit
(Standards §8.1) and the confirmation states the difference being accepted, if
any.

### 5.5 Period status

One row per period: period, fiscal year, state, journal entry count, unposted
entry count, unreconciled item count, and the pre-close check result.

`03_ACCOUNTING.md` requires pre-close checks. They are shown here as a
checklist per period — each check passing or failing with a drill-through to
the offending records. A close is not a single button an accountant presses
hopefully; it is a checklist they work down.

**Row visual:** `danger` if the period is past its close date with failing
checks; `warning` if open past close date; `success` if closed; `muted` for
future periods.

**Actions:** Run Pre-Close Checks, Close Period (confirmation required, states
irreversibility), Reopen (administrator only, always audited).

### 5.6 Reporting

Standard set: trial balance, P&L, balance sheet, AR aging, AP aging, tax
summary, inventory valuation, GL detail.

Every report:

- states its parameters and the date/period it was run for, on the output
- is exportable
- drills through from a line to the entries behind it wherever the platform
  permits

The last is what makes a report trustworthy: an accountant who cannot get from
a total to its constituent entries cannot sign off on it, which is precisely
what `03_ACCOUNTING.md` acceptance demands.

### 5.7 Acceptance

An accountant can post a representative month and confirm every tie in
`03_ACCOUNTING.md` acceptance from screens and reports, reaching the entries
behind any figure without leaving the ERP.

## 6. Integration

Serves `09_MAGENTO.md` and `12_INTEGRATION_CONTRACTS.md` (neither of which
exists yet — see the dependency note at the head of this document). Structure
is specified here; message types and payload detail come from those documents.

### 6.1 Queue

Columns: message ID, received/created timestamp, direction (In / Out), type,
reference (the order number or SKU the message concerns) `(exp)`, attempts,
next retry, state.

**Default filter:** not successfully processed.
**Default sort:** timestamp ascending — oldest stuck message first.
**Named filters:** *Pending*, *Retrying*, *Failed*, *Dead Letter*, *All*.

**Row visual:** `danger` failed or dead letter; `warning` retrying; `success`
processed; `muted` superseded.

The **reference** column is not optional and is the `expand` column. An
integration queue whose rows cannot be tied to a business document is
unusable during an incident, which is the only time anyone opens it.

### 6.2 Failures

Failed messages with the error, the payload, the attempt history, and the
business record the message concerns.

Each failure shows: what was being attempted, in business terms; the error, in
whatever terms the remote system gave; and the resulting state of the business
record. All three, because the question during an incident is always "did the
order get through" and neither the payload nor the error answers it alone.

### 6.3 Dead letters

Messages that exhausted retries. Requires explicit human disposition — Replay,
Discard, or Resolve Manually — and every disposition is recorded with who and
why (Standards §14). A dead letter cannot be silently deleted.

### 6.4 Replay

Replay is a wizard, never a bare button (Standards §8.3). It:

1. shows exactly which messages will be replayed and their business references
2. warns where replay may duplicate a business effect
3. summarises before committing
4. records the replay and its outcome against each message

Bulk replay requires confirmation stating the count (Standards §8.2).

### 6.5 Reconciliation

Compares the ERP against the remote system for a chosen scope and date range,
listing differences: records present in one and not the other, and records
present in both whose key fields disagree.

Every difference drills through to both sides. Resolution actions are explicit
and audited; nothing auto-resolves.

### 6.6 Acceptance

During an incident, an administrator can determine which business documents are
affected, what failed and why, and replay safely without creating duplicates.

## Cross-screen acceptance

Beyond the per-screen acceptance above, the whole set is accepted when the
`11_UI_UX.md` acceptance criterion holds: a user can complete the most common
sales, purchasing, inventory and accounting workflows without unnecessary
navigation or confusing states.

Tested as five scripted end-to-end runs, each performed by the user who will
actually do that job, with navigation counted:

1. Phone order → confirm → ship → invoice → payment received.
2. Reorder need identified → PO raised → partial receipt → bill matched →
   discrepancy resolved → paid.
3. Stock enquiry → lot traced → shipment identified.
4. Month-end: pre-close checks → corrections → close → statements reviewed.
5. Integration failure → diagnosed → replayed → reconciled.

A run that requires returning to a menu mid-task is a finding against this
specification, not user error.
